## Implemented and built; physical phone retest pending

- Camera retry on cooldown, separate camera resume, heading and gyroscope events in the physical context state, and microphone read-failure cleanup. Thermal pause, cooldown recovery, and microphone resume are device verified. The device heats back to severe within a short sensing session, so sustained camera availability remains unverified.
- Explicit visible-app trip recovery can reuse an ACTIVE local trip after an abrupt process death. This path is built and installed but has not been exercised on the phone.
- User-triggered CameraX still capture, center text crop, consent-gated Sarvam Document AI OCR, and optional review/save of OCR text with provider and image fingerprint. The photo is held in memory for the request and is not saved locally by default.
- Review/save of spoken transcript, persistent source-linked trip evidence, offline evidence readback, and validity-window-aware conflict detection.
- A dim selected capture turns on the torch only when recent luminance is below 100/255 and a flash unit exists, waits 500 ms, captures, then requests torch off. The threshold was raised after a real dim setup measured 89/255 under camera auto-exposure. The policy passes a device test. In a later real phone run, the scene luminance was 12/255, on-device scene analysis completed, and the capture-light diagnostic reported `Torch off` afterward; ending the trip stopped camera, mic, and location. This confirms the automatic selected-capture path ran, although the torch transition was not independently measured with a hardware probe.

- The latest conductor-question UI build was installed after the dim-light check, but its screen flow has not yet been manually exercised. Offline readback with saved real evidence remains untested on the phone. The separate rapid-capture queue is built, but that exact queued timing was not independently asserted. The scene question path uses the selected photo, labels object descriptions tentative, and refuses to infer an exact boarding point from objects alone; its question, translation and reviewed speech controls are built but not yet manually exercised together on the phone.
- Deterministic source-gated weather/conflict alert proposals are built. A sourced forecast recommendation can post a deduplicated trip notification, while a `NO_ALERT` or stale forecast cannot. Device tests passed for the policy; notification delivery during a live risk event has not been verified.
- Minimal expandable Android sections now expose OCR translation and reviewed speech, typed two-way translation, tentative fare/time proposals, saved destination comparison, conservative bus-board checking, curated culture and coir lookup, offline reviewed phrases, source-linked evidence deletion, and conflict review/resolution. The app opens on the physical phone; the newly added feature flows still need individual phone checks.

The provider's blocks have no calibrated confidence; the UI does not invent one. The multilingual phone path is built but awaits a device retest.
- The bus section can translate a traveller-written conductor question into the local language, show it for editing, then speak it aloud only after review. This is built but not yet checked on the phone.

## Not complete against the PRD

- On-device Mirage is integrated and a real selected photo produced structured cues. The scene question guard is wired and device-tested with fixtures, but a live human-checked ticket/boarding answer and validated Malayalam sign reading are not complete.
- The two-way conversation demo is working, but it has no fluent-human translation review, local-person identity verification, full conversation history, or long-call mode. Typed and curated-source controls still need Android flow verification. No verified route/GTFS dataset, official structured weather warning feed, or production alert delivery is installed. The bus check links to official KSRTC depot enquiries, and unknown routes stay unknown. The [IMD API reference](https://api.imd.gov.in/public/api_reference.html) lists district warnings, but direct calls here returned API-key and IP-whitelist errors; the app links to the [official Kerala warning page](https://mausam.imd.gov.in/thiruvananthapuram/) for manual review.
- No complete offline ASR/vision package, downloadable maps, preferences/accessibility flow, production authentication, HTTPS deployment, lifecycle recovery proof, or 30-minute power/thermal benchmark.
- The Android screen now has a compact trip and conversation view with expandable sign, weather, memory and diagnostics sections. It has not had a TalkBack or accessibility audit.

## Run locally

1. Put `SARVAM_API_KEY` and `YATRALENS_DEV_TOKEN` in the ignored `.env` using `.env.example` as a template.
2. Install `backend/requirements.txt` and run `uvicorn backend.app.main:app --host 127.0.0.1 --port 8000` from the repository root.
3. Run `adb reverse tcp:8000 tcp:8000` with the unlocked phone attached.
4. Build from `android/` with `.\gradlew.bat :app:assembleDebug`; install `android/app/build/outputs/apk/debug/app-debug.apk`.

The debug APK contains only a disposable development token. It contacts `127.0.0.1` through ADB reverse; it is not a deployable production client.
